# World of Bagarre (par VibePandrezz) : entrée pour Claude Code

Anciennement SpookyBagarre (renommé le 17 oct. 2026) : le dépôt, l'adresse du site, les clés de sauvegarde (`spookybagarre.*`) et le préfixe du réseau gardent l'ancien nom (ne pas les changer : réglages, tournois et parties en ligne en dépendent). Le jeu n'est plus seulement « spooky » : c'est la bagarre zinzin, un fourre-tout de la baston.

Guide du projet pour qui veut l'avancer (toi, un pote, ou son Claude Code). Les notes privées du créateur (comptes,
crédits, chemins de sa machine) sont dans `CLAUDE.local.md`, non publié.

Jeu de baston à la Smash Bros : graphismes en 3D, combat en 2D (plan z = 0), jusqu'à 4 joueurs, local ou en ligne.
Three.js sans build (import map dans `index.html`), JavaScript en modules ES, réseau PeerJS (WebRTC).
Publié sur GitHub Pages : <https://redpandrezz.github.io/SpookyBagarre/> (dépôt `redpandrezz/SpookyBagarre`).

Le projet est en français : échanges, docs, textes du jeu.

## Règles de travail

- **Pas de commit ni de push sans demande explicite.** Republier le site = commit + `git push` sur `main` (GitHub Pages se met à jour tout seul).
- Ne jamais publier : photos de vraies personnes (`refs personnages/`, `tools/art/friends/`), `CLAUDE.local.md`, journaux de tâches (`*ledger.jsonl`), `*.log` (voir `.gitignore`).
- Le travail non commité est le travail en cours : ne pas l'annuler, le déplacer ni le « nettoyer ».
- **Tests toujours muets** : `?quick=1` est muet d'office ; sinon ajouter `&mute=1`. Ne jamais ouvrir le menu sans `&mute=1` (une touche débloque l'audio).
- Services payants (Meshy, Tripo, Uthana, PixelLab) : clés d'API (`MESHY_API_KEY`, `TRIPO_API_KEY`, `UTHANA_API_KEY`, `PIXELAB_API_KEY`) seulement dans les variables d'environnement de l'utilisateur, jamais écrites dans le projet, affichées ni recopiées.
- **Ne jamais dépenser sans accord** : uniquement les crédits existants, jamais d'achat. Une étape payante à la fois : lancer, vérifier le résultat (le regarder, le mesurer), le montrer, attendre l'accord avant la suivante. Lire le solde avant chaque lot, journaliser chaque tâche (`ledger.jsonl`, non publié). Une seule tentative par objet (un échec peut avoir été débité).
- Images de référence et sprites d'impact : Codex ; ses copies échouent souvent : `python tools/art/codex_recover.py <dossier> [noms]`.
- Outils Python : Python 3 avec `numpy` et `Pillow`. Node pour les tests de netcode (`tools/dev/*.mjs`).
- Fins de ligne : beaucoup de fichiers sont en CRLF, d'autres en LF. Les préserver (vérifier avec `git diff --ignore-cr-at-eol --stat`).

## Lancer et tester

- Serveur : `Jouer.cmd` ou `python tools/serve.py 8642`, puis <http://localhost:8642>. Il peut s'être arrêté entre deux sessions : le relancer.
- Match de test : `?quick=1&chars=<a>,<b>&humans=1&dev=vpad0&bot=0&hazards=0&stage=cemetery` (manette virtuelle `window.__vpads[0] = { axes:[mx,my], buttons:{a,x,jump,shield,grab} }`).
- Matchs CPU : `?quick=1&chars=a,b,c,d&humans=0&stage=<id>&mute=1`. Vérifier les erreurs avec un écouteur `error` / `unhandledrejection` (les 404 de `assets/music/*.mp3|ogg` sont des essais de formats, normaux).
- `tools/dev/posecheck.js` : fige la boucle, `P.stepN(n)` avance de n images, `P.go(slot, move, ...)`, `P.strip(...)` planche d'images. Neutraliser `__app.renderer.kick` pour des captures propres.
- `tools/dev/balance.js` : matchs CPU sans affichage, stats par perso et par coup. Mesure de référence : éjections − chutes par match sur 800 matchs (deux graines) ; écart −0,43 à +0,47 au 14 oct. 2026, −0,28 à +0,46 au 16 oct. (même mesure en Node, plus rapide : `tools/dev/balance.mjs`).
- `tools/dev/propsheet.js` : planche des accessoires 3D.
- Banc d'animation : `?animtest=<id>&anim=states|moves|walk|run|<coup>&yaw=<deg>`.
- Remplacer les entrées de tous les joueurs : surcharger `__app.match.inputs` (retourne `{ slot: { mx, my, held, pressed } }`).

## Architecture

- `src/sim/` : simulation déterministe à pas fixe 60 Hz (`World.step(inputs)`), RNG à graine. Persos dans `src/sim/chars/` (`normals()`, `dashAttack()`, 4 spéciaux), réglages des spéciaux dans `specialTuning.js` (plus de temps de recharge : voir « Priorité des coups et retour sur le terrain »), contrôles et physique dans `fighter.js` (course : coup sec du stick en ≤ 4 images, ou double appui, au clavier la course part dès l'appui (bit `DIGITAL` des échantillons), Ctrl = marcher (stick à 0,6) ; clavier 1 : ZQSD, Espace saut, clic gauche A, clic droit X, Shift bouclier, E chope ; A dans les `SMASH_WIN` = 5 images après le coup sec = smash, pas coup de course ; stick droit = A + direction 70 ms, géré dans `input.js` ; après un B+haut, l'esquive aérienne (une fois) et les aériens restent possibles, puis on redevient impuissant (`adHelpless`, `helplessAfter`) ; accroupi, saut, plateformes fines), bots dans `bot.js`, arènes dans `src/sim/stages/`.
- `src/render/` : affichage. Squelettes et poses : `src/render/rig/` (`animator.js` ressorts, `poser.js` poses + couches de clips natifs, `library.js` poses procédurales, `nativeClips.js` / `nativeMoves.js` clips Tripo et Uthana, `chars.js` / `friendRigs.js` réglages par perso). Impacts : `fx.js`, `hitSprites.js`, `particles.js`. Accessoires 3D : `propModels.js` (`fitProp`, table `FIX`).
- `src/core/input.js` (manettes, clavier, saut au stick), `src/core/settings.js` (réglages en localStorage), `src/ui/` (menus, HUD, vitrine de sélection).
- Interface en pixel art (direction « Crypte », 14 oct. 2026) : tout est posé sur une grille virtuelle 640×360 (`src/ui/pxgrid.js`, boîtes `.px` mises à l'échelle par `--k`). Scène des menus `src/ui/crypt.js` (fresque `assets/ui/crypt/fresco.png` où les potes sont peints, brouillard, chauves-souris, bougies, gags), dalle de tombeau des transitions `src/ui/slab.js` (`Screens.go(fn)`), styles `css/crypt.css`, HUD `src/ui/hud.js`. Filtre pixel sur la 3D (combats et menus) : option « Filtre pixel » (`settings.pixel` : 0, 360, 540, 720), appliqué à chaud par `renderer.setPixels` ; l'ancien rendu « rétro N64 » (au chargement) y est converti. Images : Codex (`tools/art/ui_crypt.ps1`, puis `codex_recover.py tools/art/ui/crypt`), mise à la grille et palette commune `tools/art/ui_cut.py`, petites pièces dessinées au pixel `tools/art/ui_kit.py` (panneaux 9-slice, cadres, portraits `kit/p40`). Captures exactes même fenêtre cachée : `tools/dev/pxshot.js` (le serveur les écrit dans `tools/dev/shots/`, non publié).
- Écran d'entrée (`Screens.gate`, le tout premier, avant le titre ; styles `.gate` dans `css/comic.css`) : sobre mais vivant (fond sombre, lueur qui respire, braises qui montent, un bouton A brillant et « pour entrer dans le monde de la bagarre » qui ondule lettre par lettre) ; A, Entrée ou un clic l'enfonce (onde de choc, flash, les lettres explosent) et lance le titre. Ce premier appui débloque aussi le son du navigateur : la musique `title` démarre avec le titre.
- World of Bagarre (17 oct. 2026, le nouveau nom : la bagarre zinzin, un fourre-tout de la baston, plus seulement spooky) : écran titre et menus sur une illustration Codex où les 12 potes se bagarrent autour d'une petite planète patchwork de tous les mondes (`assets/ui/wob/fresco.jpg`, quand elle est là `src/ui/crypt.js` passe en mode `wob` : plus de bougies, de lune ni de chauves-souris, des impacts « POW ! » sur les côtés `impact`, des rayons qui tournent derrière le logo `rays`, un coup de poing au lieu du tonnerre). Logo `assets/ui/wob/logo.png` / `logo_s.png` (menus, résultats) ; sur l'écran titre il est en 3D (`src/ui/logo3d.js`, `Logo3D`) : pas un modèle, le logo peint lui-même extrudé (contours de son alpha par marching squares, trous compris, biseau, flancs bleu marine, la face = l'image exacte, un reflet qui passe), il arrive en vrille, s'écrase (`onSlam` : son, secousse, impacts), flotte, penche vers la souris, s'envole quand on appuie sur A ; son propre canevas WebGL transparent par-dessus la grille 640×360 (l'image 2D reste en secours sans WebGL). Vignettes des arènes peintes (`assets/ui/stages/<id>.jpg`, `PAINTED_THUMBS` dans `screens.js` ; une arène sans vignette garde le rendu de sa scène 3D). Images : `tools/art/wob.ps1` (titre, logo, une vignette par arène d'après sa peinture et son sol en références `-i`), puis `python tools/art/wob_prep.py` (détourage du logo, recadrage 16:9). Textes : « bagarreur » au lieu de « monstre ».
- Direction « BD d'horreur » (15 oct. 2026), par-dessus la Crypte : sélection des persos, des arènes, HUD, listes et écran de victoire en comics d'horreur (encrage épais, trames, cases penchées, cartouches jaunes, onomatopées). Styles `css/comic.css` (chargé après `crypt.css`, polices Bangers et Barlow Condensed), effets `src/ui/juice.js` (`burst` « BAM ! », `splash` d'encre, `lines` de vitesse, `flash`, `fitText` pour les noms longs). Écran de victoire = couverture de BD (logo, numéro, « À LA UNE »), caméra de clip sur le vainqueur (`Showcase.startVictoryCam` : plongée puis plans coupés). Fin de match : le dernier KO part en ralenti ×0,25 pendant ~2 s (`END_SLOW` dans `world.js`), le commentateur crie une phrase de victoire (`victoryLine`, `commentator.js`) écrite en grand (`banner.vic`), puis l'écran de victoire tout de suite. Duels (deux combattants restants), comme Smash Ultimate : un coup qui va éjecter (trajectoire jouée d'avance par `World.lethal`, avec 8 % de marge pour le DI) fige l'impact en ralenti ×0,3 (~1 s) et la caméra plonge dessus (`CameraRig.zoomIn`, lignes de vitesse `zoomlines`, son `kozoom`) ; un très gros coup qui ne tue pas, un zoom plus court (au plus toutes les 3 s, `zoomCd`). Sur 24 duels CPU : 89 % des zooms KO tuent vraiment. Bougies de l'accueil : seules les deux grappes peintes respirent (`CANDLE_ZONES`, `crypt.js`), plus aucun pixel qui clignote.
- Musiques (`src/audio/tracks.js`) : `title` (17 oct. 2026 : l'écran titre, le menu, le choix des persos et des arènes, les autres menus ; une seule chanson qui continue d'un écran à l'autre sans redémarrer, lancée dès le démarrage du jeu quand le navigateur le permet, sinon au premier clic ou à la première touche), plus aucune musique procédurale (`music.js` ne joue plus : un écran sans fichier est muet), `menu`, `battle1..`, et facultatifs `titre`, `persos`, `victoire` (une fois, puis `resultats` ou le menu), `options`, `salon`, `finale`, `go`, `combat_<arène>`.
- En ligne : `src/net/net.js` (PeerJS, ou onglets du même navigateur avec `?net=local`), `src/game/session.js` (salon : quand tout le monde est prêt, n'importe quel joueur appuie sur START et choisit l'arène (`lobby.chooser`), les autres, l'hôte compris, regardent ; il décide aussi de la suite aux résultats ; l'hôte sans perso est spectateur), `src/net/rollback.js` + `src/game/rollbackMatch.js` (rollback, voir plus bas). L'ancien mode (l'hôte envoie des images, `src/game/clientMatch.js`) reste accessible avec `?netmode=snap` chez l'hôte.
- Modèles : 8 persos sur rig Tripo (`tools/art/tripo_pack.py`), 8 sur squelettes Blender recevant les mêmes clips (`tools/art/legacy_pack.py`, originaux dans `tools/art/legacy_old8/`). Les deux scripts ne gardent que les clips utilisés (`used_clips()` lit `poser.js` et `nativeMoves.js`).
- PPROD (18e perso, Meshy, même chaîne) : `src/sim/chars/pprod.js`, `src/render/rig/pprodRig.js` (chaise et PC Meshy dans `assets/models/props/`, pièces, pizza, spaghettis faits en code), clips dans `CHARACTERS.pprod` de `meshy_pack.py`.
- SKANKY (19e perso, Meshy, même chaîne) : `src/sim/chars/skanky.js`, `src/render/rig/skankyRig.js` (skate de Nymano sous ses pieds, portique fait en code, train Meshy `assets/models/props/train.glb`, bulles de mots), clips dans `CHARACTERS.skanky` de `meshy_pack.py`.
- Epektase (17e perso, Meshy) : ses animations sont toutes à lui (`NATIVE_MOVES.epektase`, `NATIVE_STATES` dans `nativeMoves.js`). Chaîne : `tools/meshy/meshy.py` (payant, une étape à la fois), `tools/art/meshy_transfer.py` (transfert gratuit de clips d'un squelette à un autre), `tools/art/meshy_pack.py` (modèle du jeu, extraits `derive`, `--prop`). Détails dans `docs/ASSETS.md`. Les sources Meshy (`tools/art/meshy/`, 200 Mo : modèles bruts, clips achetés) restent sur la machine du créateur, non publiées.
- Allonge des coups : pendant un coup normal, `src/render/rig/reach.js` étire le membre (ou l'arme, `cfg.reach.weapon`) qui frappe jusqu'à sa zone de frappe et fait avancer le corps (jusqu'à 0,5 m, à l'affichage seulement) ; les zones de frappe trop longues sont recalées dans `src/sim/chars/reachFit.js` (membre tendu + 0,3 m, au moins 65 % de l'ancienne portée). Vérifier avec `tools/dev/reachcheck.js` (`sheet` : planche avec les zones en rouge, `measure`, `fitTable`). Un nouveau perso ou un coup changé : refaire la mesure.
- Mini-jeux (« ultis », `src/sim/minigames.js`, affichage `src/render/minigameView.js`) : **toutes les 60 à 80 s de combat, au hasard (70 s en moyenne)** (`tickMinigameClock`, horloge `W.mgClock`, délai tiré `W.mgNext` ; `rules.mgEvery` = un délai fixe en secondes, 0 = jamais tout seul ; rien ne s'affiche avant les 5 dernières secondes : le HUD annonce alors le jeu qui vient, tiré d'avance `W.mgNextKind`, `mgNextName`), le match se fige (`W.mg`, dans `WORLD_KEYS`) et deux combattants tirés au hasard jouent un mini-jeu **tiré au hasard** (`pickKind` : un sac mélangé `W.mgBag`, où le duel au pistolet compte `FPS_WEIGHT` = 3 fois, jamais deux fois le même de suite). Menu principal → MINI-JEUX : lancer chacun à part (toi contre CPU ou CPU contre CPU, CPU facile par défaut : réglage « Niveau du CPU »), pour tester. Les mini-jeux passent dans une télé cathodique dessinée par-dessus le combat figé (grisé autour), en « 2,5D » : boîtier en bois avec son épaisseur, suspendu au plafond par deux câbles ; il tombe, les câbles le rattrapent (petit rebond), il se balance puis se calme (`tvPose`, `drawTVBody`, `drawTVScreen` ; `TV` = l'écran dans la grille 640 × 360). Le jeu se dessine directement dans l'écran penché (`drawTVScreen(off, cw, ch, content)` : la grille 640 × 360 posée sur l'écran ; jamais sur un canevas à part recopié ensuite, la recopie forçait le navigateur à finir le dessin sur-le-champ, 5 à 17 ms par image), puis le verre par-dessus : une image faite une fois (`crtOver` : lignes de balayage douces, phosphore à peine visible, coins sombres, reflet ; plus de shader dans un moteur WebGL à part, qui coûtait 3 à 40 ms par image), couleurs du jeu intactes ; un jeu en 3D (duel, pluie de Pandrezz, vapoteuse) est rendu par le moteur dans le cadre de l'écran (`renderer.tv`, un peu plus grand que l'écran) et se voit à travers l'écran percé de la télé, tenue droite (`this.flat`) : aucune recopie de l'image 3D (`renderer.tvCopy = false` ; recopier une image WebGL vers un canevas 2D coûte très cher sur Safari et les petites machines) ; un jeu en 2D se joue sur le combat figé (`renderer.frozenCanvas`), comme avant la télé. Tout ce qui ferait un à-coup est préparé d'avance : pendant le « 3, 2, 1 » du match (`prewarm` : le verre, les polices à plusieurs tailles, les marionnettes de tous les jeux, des commentateurs et du toktok, la scène du duel), pendant la descente de la télé (`warmQ` : marionnettes du jeu, son `warm`, sa première image dessinée pour rien `dryRun`) ; au « 3, 2, 1 » aussi les fantômes de la facture de chaque joueur (`prepGhost(W, slot, false)` puis ses shaders à l'image suivante), les shaders du combat figé (`renderer.warmFreeze`) et les persos qu'un jeu montre en plus de ses `puppets` (`cast`, ex. les potes des vidéos de « Ne rigole pas »). Un objet 3D se prépare avec `warm3D(obj)` (shaders et textures, même de ce qui est caché : `compile` de three.js saute les objets cachés). Marionnettes (`src/render/puppets.js`) : toutes celles d'une image sont rendues ensemble dans les cases d'un atlas WebGL (4 x 3, qui garde ses cases : `preserveDrawingBuffer`), d'où on les colle directement, au début de l'image suivante (une image de retard), chacune une image sur 2 à 4 selon la qualité (`setPuppetQuality(résolution, every)`), sans antialiasing ; la première fois, tout de suite. Ne jamais dessiner dans un canevas à part pour s'en servir aussitôt à chaque image (Reyji, « Ne rigole pas » le faisaient) : sous Chrome Windows, ça bloque la carte graphique ; dessiner la marionnette directement, avec la transformation voulue. Une machine modeste (4 cœurs ou moins, peu de mémoire) ou Safari commence en qualité 1 ; le calque des mini-jeux est au plus à 1,5 pixel par point. Mesurer : `tools/dev/mgperf.js` (dans la console d'un match CPU, fenêtre visible : `start([jeux])` puis `report()` et `log`, le détail par fonction des images lentes) ; sans fenêtre à soi : `node tools/dev/mgbench.mjs [all | jeu,jeu] [port] [nom]` (un vrai Chrome hors de l'écran, sans le ralentissement des fenêtres cachées, joue tous les jeux à la suite : bilan dans `tools/dev/shots/<nom>.txt`) ; ce que le JS ne voit pas (le dessin fait par Chrome au moment de passer l'image à la carte graphique) : `node tools/dev/mgtrace.mjs <jeu> [port]` (trace Chrome résumée par fil ; `SUMMARY=1`, `PHASE=outro`, `PRE='<js>'` pour couper une partie du dessin et voir ce qu'elle coûte). Banc du 17 oct. 2026 : `mgbench_before.txt` / `mgbench_after.txt`. Pendant la facture, la caméra plonge sur chaque coup du fantôme (`zoomIn`, de plus en plus près, le dernier plus long) puis dézoome sur l'éjection. Pas d'explication : à la fin du compte à rebours, la télé descend et s'allume (la ligne blanche, le nom et le but à l'écran ; `MG_INTRO` = 0,5 s), puis le jeu (10 s ; la voix dit le but, les 3 premières secondes montrent sous la télé le but et les touches de chaque joueur de ce PC, `keys`, `drawKeys`), « EZ WIN » (`MG_WIN`), la télé s'éteint (l'image s'écrase en un point) et remonte aussitôt, avant le retour dans l'arène (un jeu en 3D rend alors déjà la main à l'arène : `tvGone`) ; de retour dans l'arène figée (`W.mgResume`, `MG_RESUME` = 4 s), le perdant encaisse ses % en une série de coups dans le vrai jeu (`HURT_AT`, `HURT_SHARE`, évènements `mgHurtHit` : sang, éclat, « +x % » au-dessus de lui, son % monte dans le HUD du combat ; `payout` ne fait que calculer les %), portés par le fantôme du gagnant : une copie translucide et lumineuse à sa couleur (une `FighterView` à part, `makeGhost` dès « EZ WIN », matières compilées d'avance, sans ombre) qui se téléporte d'un côté à l'autre du perdant et joue de vrais coups (jab, tilt, aérien, smash) calés pour toucher pile aux coups, puis la caméra recule (tout le monde dans le cadre) et « PRÊTS ? 3, 2, 1 » (`MG_READY` = 1,2 s, le temps de reprendre ses esprits), puis le coup final du fantôme qui l'éjecte pendant que tout repart, caméra large (`stepResume`, `mgStrike`), faux succès façon Steam, et pendant la facture un téléphone « toktok » à gauche (deux vidéos qui se moquent du perdant, likes et commentaires des potes, `TOK_VIDS`, `TOK_COMS`) et trois commentateurs (persos absents du match) qui surgissent en bas avec leur pique (`MOCK_LINES`, `startMock`, `drawMock`) ; le flash info télé ne tombe qu'une fois sur deux, entre 0,5 et 4 s après (`newsLater`) (tout ça : affichage seul). Les 6 premiers jeux sont dans `minigames.js` / `minigameView.js` ; les suivants ont chacun leur fichier dans `src/sim/mg/` et `src/render/mg/` (contrat, aides et sons : `src/sim/mg/README.md`). Les jeux (28) : duel au pistolet, bonbons (`candy`), tiercé (`horses`), bonne parole (`moral`), danse, bistouri (`surgery`), baffes (`slap`), frisbee, pluie de Pandrezz (`coins`), larbin de J'san (`lol` : une seule chose réclamée à la fois, chacun signe ses actions), Reyji (`dog`), grimpe (`climb`), enfer des balles (`bullet` : chacun sa moitié d'arène, la même pluie de balles en miroir, on ne fait qu'esquiver, le moins touché gagne), et depuis le 16 oct. 2026 : médiator d'Epektase (`mediator`, remplace l'accordeur), échecs (`chess`), calcul mental (`math`), 49.3 de Micron (`macron`), évasion de la télé (`tvbreak`), master poulet (`chicken`), home run (`homerun`), verre parfait (`tap`), toilettes propres (`toilets`), promenade de Reyji (`walk`), faux papiers de Skanky (`papers`), drague de Skanky (`dating`), ne rigole pas (`nolaugh`), Tetris express (`tetris`), haltères de BIDO (`dumbbell`), casse-briques de BIDO (`breakout`), trial (`trials`), lave-vitre lofi de Nymano (`window`), sniper des corbeaux (`birds`), vapoteuse de J'san en 3D (`vape`), battle d'aura (`aura` : les mèmes TikTok, « +1000 AURA » au bon moment, « 6-7 » = alterner ◀ ▶ le plus vite possible). Qui est qui : pendant le jeu, les deux étiquettes en haut (`drawTags` : tête, pseudo, perso, à la couleur du joueur, « CPU » ; J1 à gauche, J2 à droite), et dans le jeu `view.who(W, M, i, x, y, opts)` près de la zone de chacun ; un jeu qui a son propre en-tête met `tags: false`. Comment jouer, là où on joue : `view.hint(W, M, i, x, y, [['lr', 'choisir'], ['A', 'ouvrir']])` (les touches du joueur écrites pour son appareil, à côté de ce qu'il pilote ; grandes 3 s puis discrètes ; rien pour un CPU), `view.keyName(M, i, 'A')` ; la bande des touches sous la télé reste tout le jeu ; les jeux d'avant ont leurs touches posées par `LEGACY_HINTS` (`minigameView.js` : où et quoi, pour chacun). Menu MINI-JEUX : la liste défile (`PixelList` `maxRows`, molette). Tout est dans la simulation (déterministe, rollback, CPU compris). ## Pièges connus

- Ne jamais enlever ni ajouter le brouillard (`scene.fog = null`) ou une lumière en cours de match : la recette de tous les shaders change et tout se recompile d'un coup (l'ultime figeait ~1 s à son début ; il repousse maintenant le brouillard très loin puis le remet). Pour voir ce qui compile en plein combat : `gl.info.programs` avant / après une image lente.
- Résolution de la 3D : un budget de pixels (`renderer.pixBudget`, ~1080p) quel que soit l'écran, qui baisse tout seul si les images traînent (`noteFrame`, jusqu'à ~1 million) ; ombres en 2048 ; antialiasing en FXAA dans la dernière passe (`uFxaa`, plus de MSAA x4 sur la cible de la scène : plus d'un tiers du temps de la carte graphique). Les grandes images (planches des impacts `vidFx.js`, atlas du laser des ultimes) sont envoyées à la carte graphique dès qu'elles arrivent (`initTexture`), pas au premier coup qui les montre. Mesurer la carte graphique : `EXT_disjoint_timer_query_webgl2` dans la console (temps d'une image, boucle du jeu en pause).

- Écrans à 144 / 240 Hz (PC de jeu) : la boucle (`App.frame`, `src/main.js`) ne dessine qu'environ 60 images par seconde (la simulation est à 60 Hz) ; avant, tout était redessiné à chaque rafraîchissement et les grosses configs sous Chrome Windows ramaient. `?fps=0` enlève la limite. Options → « Compteur d'images (FPS) » (`settings.showFps`) : un petit compteur en haut à gauche (images par seconde, pire image de la demi-seconde en ms ; vert, orange, rouge) : à demander à quelqu'un dont le PC rame. Les textes des mini-jeux sont écrits une fois dans une petite image puis collés (`text`, `TEXT_CACHE`), et tous les `fillText` / `strokeText` du calque aussi (`src/render/textSprites.js`, `cacheCanvasText`) : sous Chrome, un texte écrit sur un canevas accéléré est redessiné lettre à lettre à chaque image au moment de la passer à la carte graphique, 5 à 8 ms invisibles dans les mesures JS (c'était la cause des ralentis des mini-jeux et des fins de jeu). Au plus 8 nouvelles petites images par image (`spriteBudget`), tailles arrondies (un texte qui grossit, des emojis de toutes les tailles). Brouillard : ne jamais l'enlever (`scene.fog = null`) ni changer son type en plein match, tous les shaders de la scène se recompilent (400 ms figées au premier ultime : l'ultime le repousse au loin à la place).

- Un `Armature` tourné : l'os du haut est relatif à lui (`preInv` dans `animator.js`), sinon le perso montre son dos quand il regarde à gauche. Toujours vérifier les deux sens.
- Les squelettes Tripo sont à l'échelle ~×2 : les décalages de hanches sont convertis dans l'échelle du parent (`sclM` dans `animator.js`).
- Les clips en boucle (`idle`, `walk`, `run`) sont nettoyés de leur dérive au chargement (`nativeClips.js`).
- Lisibilité : pas de fumées ni d'effets qui couvrent l'écran (choix du créateur) ; secousse et flou plafonnés (`camera.shake`, `renderer.kick`).
- Codex depuis PowerShell 5.1 : script en UTF-8 avec BOM, pas de guillemets droits dans les descriptions (mettre “ ”), le texte avant `-i` (qui avale plusieurs fichiers). Il ignore souvent le fond magenta demandé : `ui_cut.py` détoure aussi les fonds unis.
